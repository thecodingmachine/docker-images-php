How it works

  
mod_php (apache variant) runs PHP inside each Apache process (mpm_prefork): a
    process is busy for the whole life of a connection, PHP or not: static files, TLS handshakes, idle keep-alive
    connections. Each process costs the memory of a PHP worker.

  
PHP-FPM (fpm variant) keeps the connections in Apache (mpm_event, built in with
    PHP_FPM_WEB_SERVER=apache) or in nginx, with cheap threads; a PHP worker is only busy while PHP runs.

  
Behind a reverse proxy, both serve about the same number of users: the proxy keeps the connections of the
    browsers. The difference is the memory and the behavior in a rush. With HTTPS served by the container, every
    connection costs a mod_php process.

  
FrankenPHP is planned as a variant of the v6 images. Its worker mode keeps the application booted between
    requests: it saves the boot of the framework, a few percent of a heavy request, far from the ×3 of “hello world”
    benchmarks. PHP runs in threads (ZTS build), a few percent slower. WordPress does not run in worker mode. Not
    measured yet: estimate only.

  

    Model
    
    
      
  • CPU per page = PHP requests × CPU time (response time minus waiting) + static files × 0.25-0.4 ms + new
        connections × (0.1 ms, + 0.9 ms for a TLS handshake); costs measured on a 2.6 GHz core, close to a cloud
        vCPU.
    • 
      
  • CPU sharing stretches the CPU time by 1 / (1 − CPU usage). A PHP request holds a worker for its waiting time
        plus its stretched CPU time; the wait for a free worker uses the Erlang C formula.
    • 
      
  • mod_php processes are also held by static files and, with HTTPS, by the handshakes (2 round trips) and, with
        keep-alive, by the idle connections of the browsers (up to 6, for KeepAliveTimeout).
    • 
      
  • Memory: base + per worker 6 MB plus the request memory, plus one heaviest request. Rush: the CPU capacity
        reduced by the contention of the PHP processes (calibrated on the measured peaks), divided by 10 when the
        memory runs out.
    • 
      
  • Best settings: the most users within 90% of the container memory, then the best rush, then the fewest
        processes. Settings you fix are kept, the other ones are optimized around them.
    •
