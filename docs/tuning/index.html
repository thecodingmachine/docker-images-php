How it works

  
mod_php (apache variant) runs PHP inside each Apache process (mpm_prefork): a
    process is busy for the whole life of a connection, PHP or not, including the idle keep-alive time of a browser.
    The number of processes must cover the connections, and each one costs the memory of a PHP worker.

  
PHP-FPM (fpm variant) keeps the connections in Apache (mpm_event, built-in with
    PHP_FPM_WEB_SERVER=apache) or in nginx, with a few threads; a PHP worker is only busy while PHP
    runs. The number of workers only depends on the CPU and on the waiting time of your requests.

  
Both reach the same CPU-bound capacity when nothing holds a connection open: fast clients behind a reverse
    proxy, keep-alive handled by the proxy. Every connection that lives longer than its PHP request (keep-alive,
    TLS, slow clients) costs a whole mod_php process, and nothing to PHP-FPM.

  
FrankenPHP is planned as a variant of the v6 images. Its worker mode keeps the application booted between
    requests; the curve is a placeholder that assumes 40% of the CPU time is spent booting the framework.

  

    Model and calibration
    
    
      
  • CPU per page = PHP CPU time × PHP requests + static files × cost of a static file (Apache 0.4 ms, nginx
        0.25 ms) + new connections × (0.1 ms, + 0.9 ms with a TLS handshake) + 0.15 ms per FastCGI request.
        Costs measured on one 2.6 GHz core.
    • 
      
  • Suggested PHP workers: 2 × CPUs × (CPU time + waiting time) / CPU time (twice what keeps the CPUs busy, for the variations of the waiting time), limited by the memory.
    • 
      
  • CPU sharing stretches the CPU time by 1 / (1 − CPU usage). A PHP request holds a worker for its waiting time
        plus its stretched CPU time; the wait for a free worker uses the Erlang C formula.
    • 
      
  • mod_php processes are also held by the static files and, with keep-alive, by the idle connections of the
        visitors (6 per browser, during KeepAliveTimeout). Behind a reverse proxy with keep-alive, the
        proxy parks idle connections on as many processes as its peak of busy ones.
    • 
      
  • Memory: shared base + per worker 6 MB plus 30% of the request memory kept by the PHP allocator, plus the
        full request memory for busy workers. Worst case = every worker busy.
    • 
      
  • Peak at twice the traffic: the CPU capacity, reduced by the contention of the PHP processes
        (1 / (1 + 0.006 × extra processes × (1 + request memory / 32 MB)), calibrated on the measured peaks), and
        divided by 10 when the worst-case memory exceeds the container.
    • 
      
  • Without keep-alive, each request of a page opens a connection: one more round trip per request in parallel
        batches of 6, two with TLS.
